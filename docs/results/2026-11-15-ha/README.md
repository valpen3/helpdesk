Фактический прогон на GitHub Actions Ubuntu, отдельный Compose project
`helpdesk-ha-ci`. [Успешный запуск CI](https://github.com/valpen3/helpdesk/actions/runs/43711947380).
Исходный код ветки: `67b6c6a`; проверенный GitHub merge commit:
`3d61a159834c735a112402d04f57b3a34f83fe09`.

Артефакты перенесены из `ha-failure-results` без изменения данных:

- [summary.json](summary.json) — инъекции, восстановления, alerts и расчёты;
- [samples.jsonl](samples.jsonl) — исходные результаты операций с timestamps.

Один процесс и одни объекты Sentinel/AMQP работали во время всех четырёх отказов.
После каждой инъекции остановленный узел возвращён в строй. Общая длительность
наблюдений — около 144,17 секунды.

Эти интервалы включают окно устойчивости 3 секунды и не равны длительности
недоступности операций. После двух выборов Redis-мастером стал `10.10.3.12`,
AMQP-клиент перешёл на `rabbitmq-3`. Redis marker сохранился; publish с confirm,
чтение quorum-очереди и проверка payload продолжились.

RabbitMQ-клиент пережил оба переключения внутри таймаута операции: проверенные
операции не вернули ошибок. Поэтому конечные MTTR/MTBF по outage для RabbitMQ
не вычисляются (`null`), а не подменяются нулём или бесконечностью.

MTBF Redis — отношение наблюдаемого uptime к двум управляемым outage.
Частоту отказов задавал сценарий: это результат эксперимента, не прогноз
эксплуатационной надёжности. Границы outage дискретны; погрешность определяется
соседними samples и таймаутами операций. Формулы и порядок повторения описаны
в [инструкции](../../ha-monitoring.md).

Также прошли проверки миграций, ACL, API gateway, Prometheus/amtool,
unit-тесты alert rules, сбор метрик и проверка мониторинга после возврата узлов.
