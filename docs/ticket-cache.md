# Кэш тикетов: зачем и как он работает

PostgreSQL хранит настоящие данные. Redis хранит временные копии ответов,
чтобы повторяющиеся чтения не нагружали PostgreSQL.

## Чтение одного тикета

```text
GET тикета → есть подходящая копия в Redis?
               ├─ да → вернуть её, X-Cache: HIT
               └─ нет → прочитать PostgreSQL, X-Cache: MISS
                          └─ сохранить копию на 300 секунд
```

TTL — срок жизни копии. После его истечения Redis сам удаляет ключ. Тикета в
базе это не касается. Несуществующие тикеты не кэшируются.

## Списки и их версии

В списке могут различаться страница, размер и фильтры. Для каждого сочетания
получается отдельный hash и ключ `tickets:list:v{N}:{hash}` с TTL 60 секунд.
Порядок query-параметров не меняет ключ. N хранится в `tickets:list_version`.

После создания или изменения тикета приложение делает COMMIT, затем удаляет
его копию `ticket:{id}` и увеличивает N одной операцией Redis. Например,
списки v7 перестают использоваться, потому что новые запросы ищут v8. Старые
списки удалятся по TTL; искать их через KEYS/SCAN и массово удалять не нужно.
Изменение одного тикета при обычной работе не сбрасывает копии других тикетов.

Смена статуса по-прежнему всегда читает PostgreSQL и проверяет version в SQL,
поэтому кэш не участвует в решении, можно ли сохранить изменение.

## Одновременное чтение и изменение

Запрос мог прочитать старый тикет из БД, пока другой запрос уже изменил его.
Если без проверки сохранить старый ответ в Redis, кэш снова станет устаревшим.
Поэтому перед чтением запоминаются эпоха и версия списков. Сохранить ответ
можно только если они не изменились. Короткие Lua-скрипты проверяют условие
и выполняют запись без вмешательства других Redis-команд.

## Сбой Redis

Ошибки соединения, таймауты и испорченный JSON не превращают рабочий запрос к БД
в ошибку сервера. Приложение пишет предупреждение и возвращает MISS.
Зависшие операции ограничены CACHE_TIMEOUT (по умолчанию 0.25 секунды на
операцию), автоматические сетевые повторы отключены. Ожидание общего lock
также ограничено: очередь параллельных запросов не умножает таймаут.

Если во время сбоя были записи, Redis мог сохранить старые копии. При первом
успешном обращении заметивший ошибку процесс создаёт новую эпоху
`tickets:cache_epoch`. Копии прежней эпохи игнорируются и заполняются заново.
Новый процесс тоже начинает новую эпоху. При смене эпохи N сбрасывается в 0;
совпавшее имя старого ключа безопасно, поскольку проверяется и эпоха JSON.

Это кэш с ограниченной устарелостью, а не атомарная транзакция PostgreSQL+Redis.
Между COMMIT и инвалидацией есть короткое окно. Если реплика, пропустившая
инвалидацию, выключилась, другие реплики могут видеть прежние копии до
смены эпохи или истечения TTL (до 300 секунд для тикета, 60 для списка).
Долговечные инвалидации требуют механизма надёжности, например outbox.

## Подключение

Клиент redis.asyncio создаётся один раз на lifespan и закрывается при остановке.
Настройки: REDIS_HOST, REDIS_PORT, REDIS_DB, REDIS_USER, REDIS_PASSWORD,
CACHE_ENABLED и CACHE_TIMEOUT. Пароли не пишутся в логи.

Compose подключает ticket-service к cache-net и ждёт healthy Redis при запуске.
Если Redis откажет после запуска, приложение продолжает работать.
`/health/ready` проверяет обязательный PostgreSQL: необязательный кэш не выводит
работоспособный сервис из готовности. CACHE_ENABLED=false отключает кэш
приложения, но не удаляет зависимость запуска Redis из Compose.

ACL-пользователи пока не включены: по плану они добавляются на этапе 3.

## Ручная проверка в Ubuntu/WSL

После подготовки .env:

```bash
docker compose up -d --build --wait
```

Создайте тикет по примеру из ticket-api.md. Подставьте его id вместо 42:

```bash
curl -i http://localhost/api/v1/tickets/42  # X-Cache: MISS
curl -i http://localhost/api/v1/tickets/42  # X-Cache: HIT
docker compose exec redis redis-cli GET ticket:42
docker compose exec redis redis-cli TTL ticket:42
```

Измените его статус с текущей версией (ниже пример для нового open-тикета):

```bash
curl -i -X POST http://localhost/api/v1/tickets/42/status \
  -H 'Content-Type: application/json' \
  -d '{"status":"closed","version":1}'
curl -i http://localhost/api/v1/tickets/42  # MISS, status=closed, version=2
curl -i http://localhost/api/v1/tickets/42  # HIT
```

Проверять отказ следует на отдельном тестовом стенде:

```bash
docker compose stop redis
curl -i http://localhost/api/v1/tickets/42  # 200, MISS
docker compose up -d --wait redis
curl -i http://localhost/api/v1/tickets/42  # MISS после замеченного сбоя
curl -i http://localhost/api/v1/tickets/42  # HIT
```

## Автоматические проверки

`make test` работает без PostgreSQL и Redis. RUN_DATABASE_TESTS=1 включает
тесты БД; дополнительно RUN_CACHE_TESTS=1 включает реальный Redis. Оба флага
установлены в задании compose GitHub Actions. Проверяются HIT без SQL-запросов,
MISS → HIT → изменение → MISS, TTL, версии списков и различие фильтров,
повреждённые записи, ошибки обновления, позднее заполнение после инвалидации,
записи при сбое и восстановление. Unit-тест также проверяет 100 параллельных
запросов при зависшем Redis: они не ожидают сетевые таймауты друг за другом.
