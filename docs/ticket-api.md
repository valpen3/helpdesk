# Четыре эндпоинта: что происходит с запросом

Эта часть этапа 2 добавляет создание тикета, чтение по номеру, список и смену
статуса. Схема БД остаётся прежней, новая миграция не требуется.

## Файлы и их назначение

- `app/schemas.py`: какие данные клиент может передать и что сервер вернёт.
  Например, пустая тема или неизвестный приоритет дают 422 до выполнения SQL.
- `app/api/tickets.py`: обработчики четырёх адресов API. Они получают сессию,
  читают/меняют строки и сохраняют изменения через commit.
- `app/domain/status.py`: единая таблица допустимых переходов статуса.
- `infra/nginx/nginx.conf`: пропускает запросы /api/v1/tickets и вложенные пути
  к приложению; служебные /health/* приложения остаются внутренними.

```text
curl → Nginx → проверка запроса → обработчик → PostgreSQL → JSON-ответ
```

## Пример использования в Ubuntu/WSL

Сначала подготовьте .env со своими паролями и запустите стенд:

```bash
docker compose up -d --build --wait
```

Создать обращение:

```bash
curl -i -X POST http://localhost/api/v1/tickets \
  -H 'Content-Type: application/json' \
  -H 'X-User-Id: 11111111-1111-4111-8111-111111111111' \
  -H 'X-User-Email: client@example.com' \
  -d '{"title":"Не работает VPN","description":"Не удаётся подключиться","priority":"high"}'
```

Ожидается 201 и JSON с id, status=open, version=1 и данными автора. Запомните
полученный id: в командах ниже замените 42 своим номером.

```bash
curl -i http://localhost/api/v1/tickets/42
curl -i 'http://localhost/api/v1/tickets?page=1&size=10&priority=high'
curl -i -X POST http://localhost/api/v1/tickets/42/status \
  -H 'Content-Type: application/json' \
  -d '{"status":"closed","version":1}'
```

После закрытия ожидаются status=closed, version=2 и заполненная closed_at.
Если повторить последний запрос с version=1, сервер вернёт 409: сначала надо
прочитать актуальные данные. Если попытаться перейти open → resolved, будет
422: такой переход не предусмотрен. Несуществующий положительный номер даёт 404.

## Зачем нужна версия

Два человека могут прочитать один и тот же тикет. Изменение выполняется как
`UPDATE ... WHERE id = :id AND version = :version`. Только один запрос сможет
изменить исходную версию; следующий увидит конфликт, а не затрёт чужую правку.
Версия проверяется при предварительном чтении и ещё раз самим UPDATE в БД.

## Границы этой задачи

Временные заголовки не являются авторизацией. Пока нет JWT, чтение и изменения
не ограничиваются ролями или владельцем; это поведение явно описано в api.md.
Все разрешённые переходы доступны напрямую через /status. Позже часть переходов
будет вызываться назначением исполнителя и добавлением комментария.

Кэш Redis теперь подключён к чтению тикета и списков: см. [ticket-cache.md](ticket-cache.md).
Изменения сохраняются напрямую в PostgreSQL, затем кэш инвалидируется.
События RabbitMQ, аудит ticket_history и эндпоинты комментариев добавляются отдельно.

## Проверки

`make test` запускает в том числе проверки входных данных без PostgreSQL.
При RUN_DATABASE_TESTS=1 также выполняются HTTP-тесты с реальной БД:
создание/чтение сохранённого тикета, пагинация и фильтры, переходы статуса,
даты решения/закрытия, отсутствие изменений после ошибки и конкурентное обновление.
Такие тесты уже подхватываются существующим заданием compose в GitHub Actions.

`helpdesk-apicheck` с новым томом PostgreSQL:

| --- | --- |

| Ruff и git diff --check | Ошибок нет |
