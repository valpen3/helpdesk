# Надёжность: целевые показатели и эксплуатация

Этот документ фиксирует цели из `docs/architecture.md` и то, что уже можно выполнить в текущем Compose. Целевые показатели не являются измеренными значениями: фактические MTBF/MTTR появятся после регулярных прогонов отказов.

## Цели обслуживания

| Показатель | Цель | Как измерять |
| --- | --- | --- |
| Доступность gateway | ≥ 99,5% за 30 дней | доля ответов без 5xx |
| Задержка чтения тикета | p95 < 200 мс | HTTP-метрики `GET /api/v1/tickets/{id}` |
| Задержка создания тикета | p95 < 500 мс | HTTP-метрики `POST /api/v1/tickets` |
| Доставка уведомления | p95 < 60 с | время от `occurred_at` до отправки письма |
| MTBF | ≥ 720 ч | время наблюдения / количество отказов |
| MTTR | ≤ 15 мин | среднее время от обнаружения до восстановления |
| Потеря подтверждённых событий | 0 | сверка outbox, брокера и обработанных `event_id` |

В формулировке задания «CLI» трактуется как SLI (Service Level Indicator): измеряемый показатель качества обслуживания. Это стоит сверить с преподавателем.

## События ticket-service

Изменение тикета и событие записываются одной транзакцией PostgreSQL. Фоновый worker публикует незавершённые строки `outbox` в RabbitMQ с publisher confirms и отмечает `published_at` только после подтверждения. Если RabbitMQ недоступен, записи остаются в БД, а worker повторяет подключение и отправку.

Падение после подтверждения брокера, но до обновления `published_at`, может привести к повторной доставке. Потребители должны быть идемпотентными по `event_id`. Старые опубликованные строки пока не удаляются автоматически; следите за размером `outbox`.

## Резервное копирование PostgreSQL

`pg-backup` сразу после запуска и затем каждые 6 часов создаёт custom-format дампы трёх баз с узла `postgres-replica` в `backups/<имя базы>/`. Скрипт проверяет читаемость каждого файла через `pg_restore --list` и удаляет дампы старше 7 дней. Каталог `backups/` находится на хосте; для защиты от потери самого хоста его нужно копировать во внешнее хранилище.

Восстановление проверяйте в отдельную пустую базу с префиксом `auth_`, `tickets_` или `sla_`. Например, в PowerShell:

```powershell
docker compose exec pg-backup sh /usr/local/bin/restore.sh /backups/tickets_db/tickets_db_<timestamp>.dump tickets_restore_check
```

Скрипт откажется перезаписывать существующую базу. После успешного восстановления проверьте таблицы и число записей, затем удалите временную БД вручную через администратора PostgreSQL. Для фактического восстановления в рабочую базу используйте проверенный дамп и согласованное окно обслуживания.

## Переключение PostgreSQL

Реплика создаётся из primary через `pg_basebackup -R`; `postgres-router` направляет сервисы на основной узел, а replica настроена как резервный backend. При подтверждённом отказе primary:

```bash
bash scripts/failover.sh --confirm-primary-is-unavailable
```

Скрипт останавливает старый primary, повышает replica до primary и ожидает, пока router начнёт возвращать `pg_is_in_recovery() = false`. После переключения старый узел оставляют остановленным: его нельзя просто запустить, так как данные разошлись. Перед возвращением узла нужно очистить его каталог данных и заново создать replica от действующего primary. Репликация асинхронная, поэтому при аварии возможна потеря транзакций, которые ещё не дошли до replica.
